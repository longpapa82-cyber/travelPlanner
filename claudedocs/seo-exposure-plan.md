### 진짜 병목 (이번 계획의 핵심)
1. **🔴 만들어 둔 콘텐츠가 배포 안 됨** — `feat/blog-bulk-expansion`(커밋 `114613cf`)에 KO/EN/JA 87개 신규 글이 있으나 **`main` 미병합 = 라이브에 없음**. 현재 라이브 블로그는 **KO 15개뿐**. → **가장 값싼 SEO 개선은 이 87개를 배포하는 것.**
2. **🔴 sitemap이 하드코딩** — `app.controller.ts:111-229` `staticUrls` 배열이 손으로 관리됨. 블로그를 늘려도 이 배열을 수정 안 하면 sitemap에 안 들어가고 → 검색엔진이 못 찾음.
3. **🟡 블로그에 hreflang 없음** — sitemap·페이지에 블로그 다국어 대체 링크 부재. EN/JA를 배포해도 언어별 연결 신호가 없어 색인 효율 저하.
4. **🟡 콘텐츠 갭** — 앱 핵심 차별점(**경비 정산·공동 여행 협업**)을 다루는 글이 0개. 이 키워드로 유입될 기회를 놓치고 있음.
5. **🟡 네이버 최적화 부재** — 네이버는 자체 블로그/카페 생태계 가중치가 높음. 정적 사이트만으로는 노출 한계. (메모리에 데일리 바이럴 자동화가 있으나 네이버는 "이메일 초안 → 수동 발행" 반자동.)

## 1. 전략 개요 — 3개 레인

```
레인 A. 파이프라인 정비 (구조)   → 늘린 콘텐츠가 자동으로 노출되게
레인 B. 콘텐츠 확장 (양·질)      → 검색 수요가 있는 주제로 글 증설
레인 C. 채널 노출 (구글·네이버)   → 색인 촉진 + 네이버 생태계 대응
```

우선순위 원칙: **구조를 먼저 고치고(A) → 이미 만든 걸 배포하고 → 새로 늘린다(B).**
순서를 뒤집으면 "글은 많은데 검색엔진이 못 찾는" 현 상태가 반복됨.

## 2. 레인 A — 파이프라인 정비 (선행 필수)

### A-1. sitemap 자동 생성으로 전환 🔴 최우선
**문제**: `staticUrls` 하드코딩 → 콘텐츠 추가 시 누락 위험.
**해결**: 블로그/가이드 URL을 `frontend/public/blog/*.html`·`guides/*.html` 파일 목록에서 빌드 타임 또는 런타임에 **자동 스캔**해 sitemap에 주입.

- 방식 1 (권장): 빌드 스크립트 `scripts/generate-sitemap-manifest.py`가 public 디렉토리를 스캔해 `blog-manifest.json`(slug·lang·lastmod) 생성 → 백엔드가 이 매니페스트를 읽어 sitemap 렌더.
- 방식 2 (간단): `app.controller.ts`의 `getSitemap`이 컨테이너 내 `/static-content/blog/` 디렉토리를 `fs.readdir`로 스캔.
- **검증**: 새 글 파일 추가 → `/sitemap.xml`에 자동 등장하는지 확인.

### A-2. sitemap에 hreflang 주입 🟡
블로그/가이드 URL마다 `<xhtml:link rel="alternate" hreflang="ko|en|ja">` 추가.
→ 구글이 언어 클러스터를 인식해 중복 콘텐츠 페널티 회피 + 언어별 정확 노출.

### A-3. sitemap 자동화 회귀 방지
`scripts/validate-content.py`에 **"public에 있는 글이 sitemap에 모두 있는가"** 검사 추가.
→ 앞으로 글 추가 시 sitemap 누락을 CI에서 차단.

## 3. 레인 B — 콘텐츠 확장

### B-1. 배포 대기 중인 87개 글 먼저 살리기 🔴
`feat/blog-bulk-expansion` 브랜치 검토 → main 병합 → 배포.
- 배포는 **선별 rsync만으로 즉시 반영**(nginx가 `/blog`를 `no-cache`로 `/static-content` 마운트 서빙 → 재빌드 불필요). 메모리 `blog_bulk_expansion.md` 참조.
- ⚠️ 병합 전 검증: 환각 slug·broken 내부링크·중복(양 조사 결과 실제 15개뿐이므로 87개가 어떤 상태인지 재확인 필요).

### B-2. 콘텐츠 갭 채우기 (신규 글) — 우선순위순
앱 차별점·검색 수요 기준. 각 글은 KO 우선, 이후 EN/JA.

| 우선 | 주제군 | 예시 제목 | 노리는 검색의도 |
|------|--------|-----------|----------------|
| 1 | **경비 정산/예산** (앱 핵심) | "여행 경비 정산 앱 없이 vs 있이: 그룹 비용 나누기 완벽 가이드" | 앱 기능 직결·전환율↑ |
| 1 | **공동 여행 협업** (앱 핵심) | "친구들과 여행 계획 같이 짜는 법 — 일정 충돌 없이" | 앱 기능 직결 |
| 2 | **비자/서류** | "주요 여행국 무비자·비자 총정리 (2026)" | 고빈도 검색·상시 수요 |
| 2 | **숙소 선택** | "호텔 vs 에어비앤비 vs 게스트하우스: 여행 스타일별 선택법" | 정보성 고트래픽 |
| 2 | **안전·건강** | "해외여행 안전 가이드: 소매치기·응급상황 대처" | 정보성·시즌 무관 |
| 3 | **여행지 가이드 확장** | 영어/일본어 가이드 6→20개로 확대 | 다국어 롱테일 |

- **목표량 제안**: 1차 12~15개(갭 핵심), 이후 월 4~8개 페이스.
- **품질 기준**: 글당 1,500단어+·related 내부링크 3개·JSON-LD BlogPosting·앱 CTA 1개.

### B-3. 이용 가이드(사용법) 페이지 신설 🟡
현재 `guides/`는 **여행지 가이드**뿐. **앱 사용법 가이드**(How-to)가 없음.
→ "myTravel로 AI 여행 일정 만들기", "경비 정산 사용법" 등 → 앱 관련 키워드 + 브랜드 검색 흡수 + 신규 사용자 온보딩.

## 4. 레인 C — 채널별 노출

### C-1. 구글 (이미 색인 중 → 촉진·품질)
- 병합·배포 후 **Search Console에서 sitemap 재제출** + 신규 URL "색인 요청".
- **Core Web Vitals** 점검(Lighthouse) — 랜딩/블로그 LCP·CLS.
- 구조화 데이터 리치 결과 테스트(구글 Rich Results Test)로 BlogPosting 검증.

### C-2. 네이버 (구조적 열세 → 별도 전략)
- 네이버는 **자체 블로그/카페** 콘텐츠 가중치가 높아 정적 사이트만으론 한계.
- 메모리 `viral_marketing_automation.md`의 **데일리 바이럴(AI 후기 → 이메일 초안 → 네이버 수동 발행)** 운영 지속 = 네이버 생태계 침투 경로.
- 네이버 서치어드바이저: 신규 배포 후 **웹페이지 수집 요청** + sitemap 재제출.
- (선택) 자체 블로그 자동발행(백엔드 → 공유볼륨) 인프라 작업 — 메모리에 "보류" 상태.

### C-3. 공통
- 블로그↔가이드↔랜딩 **내부 링크 허브** 강화(토픽 클러스터: "경비 정산" 허브에 관련 글 모으기).
- OG 이미지 품질 점검(공유 시 썸네일).
